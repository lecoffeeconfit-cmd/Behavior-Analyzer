# Billing integration status: test-only, live charges disabled

No Stripe account, price, webhook endpoint, Supabase project, database, or paid AI key was configured in this work. The source includes a secure test-mode integration boundary and tests. It does not claim a live subscription service or an end-to-end verified payment integration.

1. Create an authentication project with email confirmation enabled, password policy, CAPTCHA/rate limits, approved redirect URLs, and recovery emails. Configure `SUPABASE_URL` and `SUPABASE_ANON_KEY` on the server. Sign-in tokens are short-lived; the client asks users to sign in again when expired. No refresh token is retained.
2. Provision PostgreSQL. Run `apps/web/server/schema.sql` as an administrator. Use a server-only database role with the privileges needed for these tables and RLS bypass or explicit service policies. Never expose `DATABASE_URL` or table mutation rights to browser clients. Enable certificate-verified TLS (`DATABASE_SSL=true`).
3. Set `WEB_ORIGIN` to the exact deployed website origin and `CHROME_EXTENSION_IDS` to a comma-separated allowlist of extension IDs. IDs differ between unpacked and store-installed extensions. There are no wildcard CORS origins and no cookie-based API authorization.
4. Choose an AI provider/model. Set the server-only key, endpoint, output cap, conservative token prices, credit limits, cost ceilings, and optionally transcription model. The provider must support the adapter's protocol. Start with a low provider project spending cap. Model capabilities such as AV synchrony or validated deepfake probabilities are **not** claimed by the default adapter.
5. In Stripe **test mode**, create a USD monthly price matching `PRO_PRICE_CENTS` (default 299). Set `BILLING_MODE=test`, a `sk_test_` key, `STRIPE_PRICE_ID`, and signing secret. The checkout route rejects live keys and mismatched prices. Test webhooks accept only non-live subscription events with the configured price and verified account metadata.
6. Use `/api/pro/checkout` with an authenticated bearer session to create a test checkout. No checkout is started automatically. The production-facing UI currently has no purchase button; this prevents suggesting that billing is already ready for customers. Server status explicitly labels configured billing as test-only.
7. Verify test subscription creation, successful/failed payment, trial expiry, cancellation, renewal, duplicate and out-of-order webhooks, price mismatch, unauthorized requests, concurrent reservations, provider timeouts, transcript duration validation, budget exhaustion, CORS, sign-out, and account recovery on the deployed staging environment. The local tests cover the request boundaries, signatures, SQL ledger, concurrency, and renewal behavior; they do not replace staging tests against your real accounts.
8. Before enabling live billing in a **separate reviewed change**, implement a customer billing portal, cancellation flow, tax/refund terms, account deletion and retention policy, monitoring/alerts, production recovery, and reconciliation of uncertain cost reservations. Replace the deliberate test-only enforcement only after the secure integration and deployment checks pass. Never simply paste a live key into this release.

Administrative controls are environment variables listed in `apps/web/.env.example`. There is deliberately no client-side administrator override. Change prices and allowances on the server; align the Stripe price with the displayed plan. Price changes may require a new Stripe price and migration policy for existing subscribers.
